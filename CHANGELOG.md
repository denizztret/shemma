## 0.32.1 — 2026-06-24 — Хотфикс: заметка с текстом роняла весь холст

### Bug Fixes

- **Заметка (note) с текстом больше не роняет холст (DRW-249).** Авто- и ручная обтяжка текста (`applyTextFitToShape`, фичи DRW-219/228/232) писала `props.w/h` для всех `TEXT_FIT_TYPES` — включая `note`, у которого в tldraw нет этих свойств (ширина фиксирована, высота авто-растёт через `growY`). `updateShape({type:'note',props:{w}})` валился с `ValidationError: note.props.w: Unexpected property`, tldraw откатывал транзакцию и показывал «Something went wrong» на **каждой** загрузке комнаты с note-с-текстом (listener авто-обтяжки видит её как `added` и фитит). На сервере данные оставались целы — битая транзакция откатывалась, `w` не сохранялся. Фикс: `note` исключён из обтяжки (он само-размерный — обтягивать по ширине нечего), `TEXT_FIT_TYPES = {geo}`, убран дублирующий `FITTABLE_TYPES`. `geo` обтягивается как раньше (ручная ⌘⇧F и авто-обтяжка); `elk-layout` не затронут (пишет `w/h` только в `geo`/`schema-container`). Тесты apply-text-fit/auto-text-fit отражают «note не обтягивается»; фронтовый сьют 822, корневой зелёный. Live-verified: комната `ios/native-modal` открывается без краша.

## 0.32.0 — 2026-06-13 — Layout-стабильность (Фазы 1–4): партиция/направление, глобальная координация строк, edge-routing на libavoid, lane-aware push + backend-паритет AI-раскладки + регулятор плотности и обтяжка текста

### Features

- **Lane-aware push при росте обёртки (DRW-242).** Точечный push соседей (`resolveOverlapsAlongFlow`) теперь группирует box-узлы в поперечные полосы и устраняет наезд НЕЗАВИСИМО в каждой полосе. Узлы из другой поперечной полосы — несвязный компонент в соседнем ряду фрейма — больше не сдвигаются по проекции оси потока при росте бокса контейнера. Раньше 1D-каскад тащил их (live-репро: рост контейнера сдвигал чужую цепочку на +240px и рвал её зазоры 340→244/244/292). Затрагивает оба пути роста: контейнер-scope ⌘⇧L (DRW-233) и ручную обтяжку текста ⌘⇧F — push внутри полосы сохранён. Frontend-only, чистая геометрия (`resolve-overlaps.ts`); новый хелпер `groupLanes` (+юниты, frontend 822). Спека `docs/superpowers/specs/2026-06-13-drw242-lane-aware-push-design.md`.
- **Сдвиг блока вместо arc-дуги (DRW-246, Фаза 4 layout-стабильности).** Только по явной компоновке (⌘⇧L / ⌘⌥⇧L), идемпотентно и детерминированно. Когда libavoid-обход невыразим штатной elbow-стрелкой (раньше — паллиативная дуга), пасс теперь сначала пробует **подвинуть один концевой блок**, чтобы маршрут стал прямым elbow'ом. Подвижный конец — лист без позиционного пина и со степенью ≤2; кандидатные позиции (рядом с партнёром, выравнивание по оси, и **уворот за полосу препятствий коридора** между концами) оцениваются повторным dry-run libavoid и принимаются только при строгом улучшении метрики, без новых наездов боксов и без ухудшения соседних рёбер; при равном score сдвиг побеждает дугу (дуга — паллиатив). После сдвига контейнер **дорастает за сдвинутым ребёнком** (узел не повисает снаружи), затем пасс перезапускается и переносит уже выразимый маршрут. Эталонный дефект A3→E2 (раньше — дуга) теперь решается опусканием E2 под колонку-препятствие: чистый elbow, дуг нет. Дуга остаётся fallback'ом, когда ни один сдвиг не проходит гейт (узкий коридор, пины). Новый чистый модуль `edge-routing-shift` (+юниты). _(DRW-247 «компактная укладка пучков» из этой фазы изъят на приёмке: сетка для звезды хаб→листья гнала дальнюю колонку в дуги — хуже одиночной колонки; задача переоткрыта на радиальный редизайн.)_ Отклонения и факты — в спеке `docs/superpowers/specs/2026-06-13-layout-phase4-placement-design.md`.

- **Стрелки обходят препятствия: edge-routing на libavoid (DRW-199, Фаза 3 layout-стабильности).** Раньше маршрут стрелки знал только о двух своих концах: длинное межконтейнерное ребро шло напрямик СКВОЗЬ чужие контейнеры и узлы (эталонный дефект A3→E2), а пучок стрелок из одного узла мог переплетаться прямо на выходе. Теперь после размещения и выравнивания (Ф1+Ф2) работает финальный пасс маршрутизации на **libavoid** (C++ роутер Adaptagrams, WASM): (1) **модель V-H «иерархическая видимость per-class»** — рёбра группируются по контейнерам-предкам концов, в наборе препятствий класса предки «раскрыты» до детей, чужие контейнеры опаковые — препятствия не пересекаются (жёсткое требование libavoid, выявлено пробами: наивные модели вели маршруты сквозь контейнеры); (2) **перенос маршрута в штатные стрелки** — стороны входа/выхода → binding-якоря, средняя линия Z-маршрута → `elbowMidPoint`; нативная реактивность tldraw полностью сохраняется (drag — стрелки тянутся); (3) **порты раздаются по маршрутам и оси потока** — порядок стрелок на стороне узла следует порядку их маршрутов (exclusive-пины libavoid + глобальная раздача позиций), переплетение пучков исчезает, а рёбра, разделённые вдоль потока, входят/выходят по сторонам вдоль него (для TB — сверху/снизу, не в бок); (4) **детуры, невыразимые elbow-каталогом** (same-side U без управляемого midpoint), получают **arc-кандидата**: точная круговая дуга с подобранной сагиттой `bend`, очищающей препятствия — эталонное ребро A3→E2 теперь обходит схему дугой; не нашлась чистая дуга — ребро остаётся как есть и помечается **метрикой невыразимости** в отчёте пасса (`window.__SHEMMA_LAST_ROUTING`; вход будущей фазы пере-размещения); (5) **метрик-гейт no-surprise** — кандидат применяется только при строгом улучшении (пересечения ребро-бокс — метрика видит и кривые геометрии — + пересечения рёбер + длина с анти-дрейф маржой): чистые веера, выровненные Ф2 линии и хорошие маршруты не трогаются, повторная компоновка идемпотентна, прогон детерминирован. WASM грузится лениво только в компоновку (~20мс; prod-сборка несёт wasm-ассетом); недоступен — прежнее elbow-поведение. Live AC#1-7: эталон 12/12 рёбер без пересечений, CI-схема 0 новых пересечений, пучок 2 перехлёста → 0, идемпотентность/детерминизм подтверждены, пины/locked нетронуты. Новые `edge-routing-core` (чистое ядро) / `libavoid-router` / `edge-routing` (+54 юнита, frontend 796).

- **AI-раскладка координирует строки так же, как ручной ⌘⇧L (DRW-245, backend-паритет Ф2).** Раньше глобальная координация строк (Ф2/DRW-235) жила только во фронтенде — `shemma_layout` через MCP и авто-раскладка domain-мутаций шли «голым» single-pass ELK (`INCLUDE_CHILDREN`), который раскладывал всю иерархию одним графом и давал иную per-container структуру, чем фронтовая per-container изоляция, поэтому строки цепочек не выравнивались (нарушение product-vision «AI рисует, как видит юзер»). Теперь чистый пасс `runGlobalAlignPass` вынесен в `@shemma/domain` (общий SSOT фронта и backend), и **`scope='all'` идёт через тот же per-container multi-pass, что и фронт** (`runLayoutSubgraph`: Pass A раскладывает детей каждого контейнера ИЗОЛИРОВАННО → Pass B top-level → Ф2 global-align → Pass C сборка), за гейтом layered-режима (для subgraph/affected и не-layered поведение прежнее, без регрессий). Три части паритета: **(1)** направление inherit-контейнеров инферится фронтовым правилом `inferInheritDir` (контейнер без внутреннего потока → перпендикулярная полоса-лейн, с потоком → вдоль фрейма) вместо backend-алгоритма external-edge-sides — иначе свежий непинованный контент раскладывался иначе, чем по ⌘⇧L; **(2)** размеры (w/h) листьев пробрасываются из ELK в Pass A — без них Ф2 считал высоту строки нулевой и соседние строки колонки наезжали; **(3)** displacement идёт ПОСЛЕ Ф2 — пасс выравнивания может положить узел на ось пина, и displacement разводит наезд по выровненным позициям. Пины и `custom`-контейнеры под обычным (не-force) пасом сохраняются — паритет с ⌘⇧L, который не трогает user-controlled контент. Чистый адаптер `global-align-adapter` нормализует abs↔parent-relative координаты вокруг пасса (per-frame scope). parity-тесты на топологии drw-218-stability + harness на реальной комнате и свежем inherit-контенте (реальный elkjs, не мок): cross-связанные цепочки на одной оси <1px, 0 sibling-overlap, идемпотентность, пины целы. Backend 1247 тестов зелёные. _(NB: `scope='all'` стал устойчив к dangling bindings — фильтрует рёбра как фронт/`scope='affected'`, а не падает в ELK.)_

- **Глобальная координация строк поперёк контейнеров: связанные узлы выстраиваются в линии (DRW-235, Фаза 2 layout-стабильности).** Раньше каждый контейнер раскладывался как чёрный ящик: порядок строк не знал о внешних связях (узел вставал не напротив своего партнёра в соседнем контейнере), а сквозная цепочка через несколько контейнеров шла зигзагом. Теперь после root-прогона работает глобальный пасс: (1) **порядок строк** в каждой колонке выбирается по внешним связям — Kahn по внутренним рёбрам + median-score соседей, направленный первый свип от истока потока, решения принимаются по уже выровненным позициям (чередование «порядок → выравнивание»); (2) **координата поперёк потока решается глобально** новым VPSC-решателем `solve1D` в `@shemma/domain` (блоки с offset'ами, fixed-вары, детерминированный topo-порядок; общий механизм с будущим 2D-пушем DRW-242) — cross-рёбра выпрямляются в строгие горизонтали/вертикали, контейнеры обтягивают результат и растягиваются при необходимости (разрыв между строками допустим, как в эталоне); (3) **separation между top-level элементами** с пересекающимися интервалами по оси потока — выравнивание не вносит box-перекрытий (на сложной CI-схеме: 0 против 5 у прототипа); (4) **выровненные рёбра получают точные центр-анкоры** в port-пассе (не участвуют в дольном распределении стороны), а их точки на границах контейнеров (`portHints`) — явный интерфейс для роутинга Фазы 3. Работает на всех четырёх направлениях доски (ось-абстракция, RL/BT — инверсия свипа), только для layered-движка; пины уважаются (pinned = fixed-вар решателя, колонка с pinned-ребёнком не переупорядочивается, force ⌘⌥⇧L игнорирует на один пасс, sizePinned-контейнер не растягивается); flip-пасс уступает участвующим колонкам. Гарантии Фазы 1 сохранены live: эталоны 0px (LR и транспонированный TB), идемпотентность 0px, партиция компонент, locked-фреймы нетронуты. `solve1D` + `global-align` (+38 юнитов; domain 158, frontend 742).

- **Стабильность и детерминизм раскладки: несвязные схемы больше не перетряхивают друг друга (DRW-218, DRW-233).** Раньше несвязные компоненты фрейма паковал сам ELK по совокупному bbox — добавление второй схемы деформировало первую, а aspect-поиск направления скорил весь граф разом и мог перевернуть фрейм от чужой правки. Теперь: (1) **партиция на связные компоненты** — каждый связный кусок раскладывается отдельным ELK-прогоном и размещается детерминированно: главная (крупнейшая) схема первой, остальные по убыванию размера **поперёк направления** фрейма (TB → колонка справа, LR → ряд снизу); одиночные свободные узлы собираются в один «хвост» вдоль направления, фрейм из только несвязанных элементов выстраивается вдоль, как раньше; нетронутая компонента получает байт-в-байт тот же layout (ноль дрейфа подтверждён live). (2) **Auto-direction оценивает только главную компоненту и «липнет» к последнему выбору** (`didrawDirectionResolved`): претендент обязан строго побить действующее направление по score (aspect + 0.15·пересечения + 0.5·наезды-на-пины) — повторные ⌘⇧L не меняют картину, вторая схема не влияет на выбор; кандидаты просчитываются параллельно. (3) **Импортированное mermaid-направление фрейма записывается как наследуемое** (`didrawDirectionInherited`) — раскладка следует ему, но авто-выбор может переинферить; явный выбор направления в панели закрепляет его и чистит маркеры, «•» сбрасывает и чемпиона. (4) **Scope = что выделено (DRW-233):** «Упорядочить»/смена направления при выделенном одном контейнере раскладывает только его содержимое — соседи отодвигаются сдвигом лишь при фактическом росте бокса, фрейм дорастает, глобальное направление не пересматривается (это же закрывает flip-scope: смена направления контейнера не флипает inherit-соседа); выделение фрейма по-прежнему раскладывает весь фрейм. Пины уважаются во всех scope (post-override; force ⌘⌥⇧L игнорирует на один проход). Новые чистые модули `component-partition` / `direction-choice` / `layout-scope` (+47 юнитов, frontend 714); live-verified на фикстуре (2 компоненты, пины, контейнер-scope), импорт-сценарии и эталоны `a-elk-tree`/`dl-test` без деградации. По приёмке добавлено (5): **несвязные компоненты внутри контейнера** (C1 = A1→A2 + изолированный A3) связываются синтетическими мостами `__bridge__N` и выстраиваются одной полосой вдоль направления контейнера — раньше elk ставил изолированный узел вторым столбцом поперёк потока (вплоть до наезда). Остаток: 1D-пуш соседей при росте бокса может сдвинуть узлы чужой компоненты по проекции оси — вынесено в DRW-242.

- **Плавный регулятор плотности раскладки вместо трёх кнопок масштаба (DRW-239).** Прежние кнопки Compact/Normal/Roomy вызывали полный пересчёт ELK (`autoElkLayout`) — flip-пасс по геометрии, рефлоу контейнеров и рост ширины боксов перетряхивали выверенную раскладку, вернуть прежний вид было трудно. Теперь в панели выделения — **ползунок «Плотность»** (0.5–2.0, центр 1.0): тащишь вправо — раздвигает выделенное, влево — сближает, **без запуска ELK**, так что направление и структура сохраняются по построению (⌘⇧L остаётся отдельным действием «перекомпоновать»). Меняются только позиции (размеры фигур не трогаем; коннекторы — bound elbow — следуют сами); контейнеры и фрейм дотягиваются по контенту — в т.ч. фрейм-предок раздвигаемого контейнера и **фрейм с закреплённым размером** (size-pin защищает от авто-раскладки, но прямой жест плотности фрейм обтягивает; он остаётся size-pinned на новом размере). Модель относительная, без «дефолта»/«нормы»: жест масштабирует снимок, снятый в момент захвата (live-превью без накопления), а откат — обычный ⌘Z (весь drag = один шаг истории). **Минимальный зазор**: при сближении коэффициент аналитически зажимается по самой тесной паре каждого уровня (равномерный scale масштабирует все попарные расстояния на один множитель), поэтому фигуры никогда не наезжают; раздвигание не ограничено. Работает для выделения / контейнера / фрейма / борда; **любые объекты-боксы** (узлы, текст, стикеры, картинки), а не только schema-узлы; выделение группируется по родителю — узлы не выпрыгивают из контейнеров; якорь — верх-левый угол для обёрток (без дрейфа) и центр для свободного выделения. Регулятор двигает и **закреплённые (pinned)** фигуры — это прямое действие пользователя (= задаёт пользовательскую позицию), а пины защищают только от AI/авто-раскладки; фигуры остаются закреплёнными на новых позициях. Board-панель «По умолчанию» сохраняет кнопки Compact/Normal/Roomy — это дефолтный spacing для нового контента / импорта / AI-агента (он не трогает уже размещённые схемы), отдельная от регулятора вещь. Чистые `computeRespreadLevel` + `levelMinK` (10 unit: spread/compress, якоря, сохранение структуры, min-gap, пины) + wiring-тест слайдера; live-verified на доске (spread/compress, экстремальное сжатие зажато без наездов, ⌘Z откатывает жест, top-level пин заморожен).

- **Кнопка «Обтянуть текст» работает по выделению / контейнеру / фрейму рекурсивно, а соседи не наезжают (DRW-232).** Прежде ⌘⇧F и кнопка обтягивали только сами выделенные geo/note: на контейнере или фрейме кнопка была видна (её видимость считалась рекурсивно по потомкам), но **не делала ничего** — её цель (`schema-container`/`frame`) не входит в обтягиваемые типы, а применение шло лишь по выделенным id. Срабатывает на авто-обтяжке (в том же шаге истории, что и обтяжка) и на **ручном drag-resize** ребёнка (по завершении жеста, AC #7); **user-pinned размер обёртки** (явный ресайз фрейма/контейнера) не трогается. (2) **Правка текста уже-обтянутого узла снова обтягивает его**: размер, заданный обтяжкой, помечается `meta.didrawSizeOrigin: "fit"`, а drag-resize/force-fit — `"user"`; авто-обтяжка переобтягивает только `"fit"`-узлы по завершении правки, никогда — `"user"` (раньше первый авто-фит ставил `didrawSizePinned` и блокировал любую переобтяжку). Push соседей и сжатие родителя остаются ручными (⌘⇧F/⌘⇧L). ## 0.31.1 — 2026-06-08 — Битый цвет/record больше не обнуляет доску при загрузке

Patch-фикс устойчивости загрузки доски (DRW-231).

### Fixes

- **Один битый цвет шейпа больше не обнуляет всю доску (DRW-231).** Сырой hex в `props.color` (например `#6A1B9A` из mermaid style-директивы, см. DRW-153) вместо именованной палитры tldraw проходил нестрогий backend-стор, но строгий `loadSnapshot` во фронтенде бросал `ValidationError` на этой записи и **прерывал загрузку всего снапшота** — доска открывалась пустой («пропали схемы»), хотя данные были целы. Лечение трёхслойное: (1) новый SSOT `coerceColor` в `@shemma/domain` (валидный enum → как есть; hex → ближайший по RGB; мусор → fallback); (2) backend `domain/schema/apply.ts` коэрсит цвет на всех путях записи (edge-overlay, set-overlay, set-container-style, set-frame-style) — hex больше не попадает в стор; (3) фронтенд `backfillStoreRecords` коэрсит уже-персистнутые битые `color`/`labelColor` до загрузки, а `loadSnapshot` обёрнут отказоустойчиво: при `ValidationError` снапшот домигрируется, записи, не прошедшие валидацию, отбрасываются (с предупреждением), а очищенный набор переотдаётся штатным `loadSnapshot` (корректно поднимает состояние редактора) — один плохой record больше не уносит всю доску, даже если он невалиден не по цвету. Проверено live-E2E: комната, обнулявшая прежний фронтенд, грузит все шейпы (цвета сведены к палитре); не-цветовой битый record пропускается, доска грузится с остальными.

Крупный feature-батч поверх 0.30.0. Главное: (1) **детерминированная feedback-телеметрия** — сервер пишет действия агента, агент опционально аннотирует, ридер `shemma feedback --diff` показывает дифф «что агент думал vs что вышло» (umbrella DRW-227.01/.02/.03); (2) **событийная авто-обтяжка текста** + явный `shemma_fit_text` (DRW-219/228); (3) **кнопка темы** — клик переключает только светлая⇄тёмная, системная по Opt-Click (DRW-230) + dark mode (DRW-217); (4) **честные коды ошибок** на всех MCP-инструментах — `daemon-unavailable` только транспорт, backend-ошибка = код+статус (DRW-221/229); (5) **hardening AI-insert схем** — elbow-стрелки, growY-aware placement, материализация групп, GC orphan-overlay'ев, MCP-policy «один фрейм = одна связная схема», формат domain-actions для агентов (DRW-205/208-220/222/224-226).

### Fixes

- **Инкрементальные стрелки — elbow.** AI-вставка (`schema-connect` через `patch_schema`) создавала arc-стрелки (кривые), тогда как импортные стрелки схемы — elbow (угловые): визуальный разнобой на одной схеме. `makeArrowShape` в `domain/schema/apply.ts` теперь `props.kind:'elbow'` (паритет с `compile.ts`).
- **Smart-insert учитывает текстовый рост узлов (growY).** Слот для нового узла считался по номинальному размеру шейпа, но tldraw дорастает бокс под многострочный лейбл уже на клиенте → новый узел мог встать внахлёст с выросшим соседом (live-репро: Alert Queue × Svc C3, 140×13px). Теперь occupants учитывают `h+growY`, а новый узел резервирует консервативную оценку высоты лейбла (`estimateEffectiveHeight`, word-wrap модель, откалибрована по живым рендерам).
- **`schema-set-overlay` стилизует существующий узел: полный style-блок.** Раньше overlay-стиль записывался только в `frame.meta.didrawOverlays` и применялся лишь при создании шейпа — «раскрась узел X» через MCP молча ничего не меняло на доске (найдено на живой приёмке). Теперь явный set-overlay обновляет сам шейп; `OverlayEntry` расширен до полного style-блока: `color`, `labelColor`, `fill` (none/semi/solid/pattern), `dash`, `size`, `font` — агенту доступно всё форматирование узла. Целевое действие выражает волю пользователя через агента и применяется всегда (`styleOwnedBy` защищает только от попутных перезаписей: role-пресеты, ре-импорт; к тому же фронтенд штампует `styleOwnedBy:"user"` даже на чисто позиционный drag — гейт по нему блокировал бы перекраску любого двинутого узла).

- **Агентский `shemma_layout` больше не разваливает доску с пинами.** Тройной фикс backend-раскладки (scope=all — путь агентов): (1) восстановление координат pinned-узлов учитывало parent-relative/absolute пространство неверно → пины «прыгали» в мусорные (часто отрицательные) координаты; (2) displacement-пасс (DRW-003) расталкивал ФРЕЙМ от его же pinned-детей (containment ≠ collision) → фрейм улетал, схема разваливалась; (3) фрейм, пересчитанный по компактному ELK-результату, схлопывался вокруг него, оставляя восстановленные пины за рамкой — теперь grow-only покрытие пинов. Плюс policy: MCP-инструкции больше НЕ советуют агенту вызывать layout после правок — раскладка пользователя переживает агентские правки; re-layout только по явной просьбе.
- **`schema-group` материализует контейнеры на доске (DRW-210).** Раньше группировка через `patch_schema` меняла только raw (mermaid): на доске контейнеры не создавались, члены не репарентились — «объедини сервисы в подгруппы» визуально не делал ничего. Теперь reconciliation-пасс в apply: каждая группа нового состояния получает реальный `schema-container` (создаётся при отсутствии — это же лечит legacy-комнаты с группами в raw и плоской доской), члены репарентятся с пересчётом координат (узлы визуально НЕ двигаются), контейнер охватывает членов (grow-only; origin clamp у края фрейма — лейбл не клипуется). Узел, покинувший группу, возвращается во фрейм; контейнер распущенной группы удаляется. Новые parent-relative позиции зеркалятся в `didrawOverlays` (reload-консистентность).
- **Layout зеркалит позиции в `didrawOverlays` — reload показывает ту же доску (DRW-209).** Backend-layout обновлял только shape-записи стора, а `frame.meta.didrawOverlays` оставались старыми; фронтовый hydrate на загрузке страницы применяет `overlay.position` поверх стора → живая WS-вкладка и свежезагруженная страница показывали РАЗНЫЕ раскладки (два источника правды). Теперь `runLayout` тем же батчем мёржит финальные позиции всех didraw-узлов каждого schema-фрейма в overlays: существующие поля записей (color/fill/pinned/styleOwnedBy/…) не теряются, записи создаются и для узлов без них; no-op writeback пропускается (повторный layout остаётся `no-changes`-фикспоинтом). Покрыты все пути layout (`/api/layout`, domain-батчи, MCP `shemma_layout`).
- **Displacement без «кучи»: вытесненные узлы — в ближайшее свободное место (DRW-208).** Старый фолбэк DRW-003 складывал ВСЕ узлы, чьи ELK-позиции пересекали пин, в одну вертикальную колонну справа от пинов — на доске с пинами по всей площади схема превращалась в нечитаемую кучу (live-репро: 21 из 23 узлов на одном x, 7 за рамкой). Теперь ездят только листья (контейнеры кроет coverage-пасс DRW-205), каждый конфликтующий лист ищет ближайший к своей ELK-позиции свободный слот (`findEmptySlot`, окна 3×/6×/12× размера узла → весь регион; occupants: пины, чужие контейнеры, уже осевшие листья; предки/потомки — containment, не collision). Колонна осталась только фолбэком «слота нет нигде». Раскладка стала фикспоинтом: повторный layout → `no-changes`.

- **Разведение «daemon-unavailable vs backend-ошибка» распространено на все MCP-инструменты (DRW-229).** DRW-221 развёл коды только на пути `applyDomain`; остальные client-методы делали слепой `r.json()` → на non-JSON 500 бросали → MCP-catch → `mapFetchError` → `daemon-unavailable` (та же конфляция на schema-write/import/fit/feedback/layout-selection и read-only GET'ах). Теперь все MCP-backing client-методы (createSchema/patchSchema/setOverlay/duplicateSchema/deleteSchema/importMermaid/fitText/feedback/layoutSelection + getContext/getCanvasView/listRooms/getState) проведены через `result()` (non-2xx аннотируется `httpStatus`, не бросается), а MCP-инструменты (schema-write, domain, read-only, canvas-view) в ветках ошибки мапят через новый guard `isBackendError`→`mapBackendError` (5xx→`unexpected-error`+status, 422→`validation-error`+status); `daemon-unavailable` остаётся только в catch (реальный транспорт). Специфичные коды сохранены (`no-client-connected` по room_url, `import-failed`/`layout-failed` для in-band 2xx, in-band `{ok:false,errors}` остаётся `validation-error`). Read-only GET'ы больше не заворачивают 500-тело как `ok:true data`. Тесты: schema-write (500 JSON + non-JSON → unexpected-error, transport → daemon-unavailable) + read-only (rooms_list/context 500 → unexpected-error, transport → daemon-unavailable).
- **MCP различает «демон недоступен» и «бэкенд вернул ошибку» (DRW-221).** Любой сбой вызова бэкенда из MCP схлопывался в `daemon-unavailable`: `CanvasClient.applyDomain` делал слепой `r.json()`, на non-JSON теле (напр. plain-text 500 от необработанной ошибки) бросал, а MCP-`runActions` ловил исключение и мапил в `daemon-unavailable` → агент видел «демон недоступен», проверял health, хотя демон был жив, а бэкенд вернул 500. Теперь `applyDomain` парсит ответ через хелпер `result()`: полученный non-2xx **не бросается** — тело аннотируется `httpStatus` и возвращается (CLI заодно перестаёт крэшиться на не-JSON 500, получает чистый объект); throw остаётся только для реального reject транспорта (ECONNREFUSED/timeout) → `daemon-unavailable`. MCP `runActions` мапит по статусу (`mapBackendError` → `mapHttpResponse`): 5xx → `unexpected-error`+status, 422 → `validation-error`+status, прочее → `http-error`. Покрыто client-тестами (500/422/200/transport) + MCP-тестами (500→unexpected-error, 422→validation-error, transport→daemon-unavailable). Scope: путь `applyDomain` (репортед-кейс); helper'ы готовы к расширению на schema/read-only пути (follow-up).

## 0.30.0 — 2026-05-31 — Schema AI-insert fixes (container-nested connect, user-triggered layout, smart-insert)

Исправления объектного редактирования v2 schema-фреймов агентом через MCP: связи к узлам внутри контейнеров теперь материализуются, AI-правки больше не перевыравнивают/схлопывают схему, новый узел вставляется в свободное место с авто-расширением фрейма.

### Fixes

- **Связи к узлам внутри контейнеров (subgraph).** `shemma_connect` / `schema-connect` к узлу, лежащему в schema-container, молча терял стрелку: резолвер эндпоинтов (`apply.ts` `findShapeByNodeId`/`extractExistingNodeIds`) искал только прямых детей фрейма. ### Features

- **Smart-insert размещение.** Новый узел при AI-вставке ставится в свободное место внутри фрейма (`findEmptySlot`); если слот не влезает — фрейм расширяется (`computeExpansion`) и узел кладётся на новый край, **не сдвигая существующие узлы** (DRW-178 helpers подключены к `patch_schema`).

### Autolayout rebuild

Полностью переработанная авто-расстановка схем (`⌘⇧L`):

- **Авто-выбор направления.** Для незакреплённого фрейма движок сам подбирает направление раскладки, дающее самую компактную схему (квадрат вместо длинной полосы) — вместо фиксированного TB/LR.
- **Flow-aware ориентация контейнеров.** Контейнер с внутренним потоком (рёбра между своими узлами) раскладывается вдоль фрейма; контейнер-«пучок» без внутренних рёбер — перпендикулярно.
- **Меньше пересечений стрелок.** Порядок узлов внутри контейнера автоматически зеркалится для распутывания связей; маршрут стрелок оптимизируется по реальной геометрии (obstacle-pass по midpoint).
- **Per-frame движок раскладки** (layered / mrtree / …) с наследуемой политикой направления.
- **AUTO-режим «•».** Кнопка «•» на фрейме сбрасывает закреплённое направление и возвращает компактнейшую авто-раскладку; cardinal-кнопки (TB/LR/RL/BT) закрепляют направление вручную.
- Явно выбранное направление контейнера/фрейма уважается и не перетирается при ре-лэйауте.
