# DRW-242 — lane-aware push (поперечные полосы) — Design

**Дата:** 2026-06-13
**Milestone:** m-8 (Layout)
**Статус:** approved (design gate пройден; LANE_EPS=1px, универсальный фикс — решения юзера)

## Goal

Точечный push соседей при росте бокса обёртки (контейнер/фрейм) перестаёт сдвигать
узлы, не пересекающиеся с выросшим боксом по **поперечной** оси. Раскладка одной
компоненты фрейма не возмущает соседнюю компоненту в другой полосе.

## Контекст и корень проблемы

DRW-232 ввёл точечный push: после роста узла/обёртки соседи, реально наезжающие
вдоль оси потока, сдвигаются вперёд минимально (`resolveOverlaps1D`). Механика
**одномерна**: `resolveOverlapsAlongFlow` (`apps/frontend/src/canvas/resolve-overlaps.ts`)
сплющивает всех box-детей обёртки в одну линию по оси потока и каскадит курсор по
проекции — **не глядя на поперечную ось**. Узел из другой поперечной полосы, чья
проекция на ось потока пересекает курсор, толкается, хотя физически не наезжает.

Путь срабатывания (единственный вызывающий `resolveOverlapsAlongFlow`):
`reflowAfterFit` → `resolveOverlapsInWrapper` (`elk-layout.ts:2255`) → `resolveOverlapsAlongFlow`.
`reflowAfterFit` зовётся из двух мест, оба через тот же чокпоинт:
- `elk-layout.ts:1025` — контейнер-scope раскладка (DRW-233), при фактическом росте бокса.
- `apps/frontend/src/canvas/apply-text-fit.ts:156` — ручная обтяжка текста (⌘⇧F).

Фикс `56db182` подавил push при отсутствии роста, но при **реальном** росте бокса
остаточный баг сохраняется.

## Design

### Подход: lane-aware push (Фаза 1 решения задачи)

Сделать `resolveOverlapsAlongFlow` **lane-aware**: после выбора оси потока
сгруппировать узлы в поперечные полосы и прогнать существующий `resolveOverlaps1D`
**независимо в каждой полосе**. Узел толкается только теми соседями, кто делит с
ним поперечную полосу.

Это закрывает наблюдаемый баг минимальной правкой. Полноценный 2D-движок (VPSC)
вынесен в отдельную follow-up задачу (см. «Out of scope»).

### Компоненты (всё в `apps/frontend/src/canvas/resolve-overlaps.ts` — чистая геометрия)

**1. Новый экспорт `groupLanes`** — разбиение узлов на поперечные полосы.

```typescript
/** Поперечная ось относительно оси потока: для axis="x" поперечная — "y", и наоборот. */
export type CrossAxis = "x" | "y";

/**
 * Группирует узлы в поперечные полосы: два узла в одной полосе ⟺ их интервалы
 * по поперечной оси перекрываются больше чем на LANE_EPS. Связность транзитивна
 * (полоса = связная компонента графа перекрытий). Возвращает массив полос —
 * каждая полоса это массив исходных узлов; порядок узлов внутри полосы и порядок
 * полос детерминирован (по возрастанию начала интервала, затем по id).
 */
export function groupLanes(
  nodes: ReadonlyArray<FlowNode>,
  cross: CrossAxis,
): FlowNode[][];
```

- Поперечный интервал узла: `cross==="y"` → `[n.y, n.y + n.h]`; `cross==="x"` → `[n.x, n.x + n.w]`.
- Два интервала `[a0,a1]`, `[b0,b1]` в одной полосе ⟺ `min(a1,b1) - max(a0,b0) > LANE_EPS`.
- `LANE_EPS = 1` (px) — гасит float-шум на стыках; полосы должны реально перекрываться.
- Алгоритм детерминирован: сортировка узлов по началу поперечного интервала
  (tie-break по `id`), линейный sweep с union в текущую полосу, пока следующий
  интервал перекрывает «правый край» текущей полосы больше чем на `LANE_EPS`.

**2. Правка `resolveOverlapsAlongFlow`** — прогон 1D по полосам.

Текущее тело: выбрать ось (`flowAxis`), смаппить в 1D items, один `resolveOverlaps1D`,
вернуть moves. Новое тело:

```typescript
export function resolveOverlapsAlongFlow(
  nodes: ReadonlyArray<FlowNode>,
  dir: string | null | undefined,
  gap: number,
): Array<{ id: string; x?: number; y?: number }> {
  if (nodes.length < 2) return [];
  const { axis, reverse } = flowAxis(dir, nodes);
  const horizontal = axis === "x";
  const cross: CrossAxis = horizontal ? "y" : "x";

  const moves: Array<{ id: string; x?: number; y?: number }> = [];
  for (const lane of groupLanes(nodes, cross)) {
    if (lane.length < 2) continue; // одиночка в полосе не двигается
    const items: Overlap1DItem[] = lane.map((n) => {
      const pos = horizontal ? n.x : n.y;
      const size = horizontal ? n.w : n.h;
      const start = reverse ? -(pos + size) : pos;
      return { id: n.id, start, size, pinned: n.pinned };
    });
    const sizeOf = new Map(lane.map((n) => [n.id, horizontal ? n.w : n.h]));
    for (const m of resolveOverlaps1D(items, gap)) {
      const size = sizeOf.get(m.id) ?? 0;
      const pos = reverse ? -m.start - size : m.start;
      moves.push(horizontal ? { id: m.id, x: pos } : { id: m.id, y: pos });
    }
  }
  return moves;
}
```

`resolveOverlaps1D`, `flowAxis`, `growOnlyBox`, `FlowNode`, `Overlap1DItem`,
`FlowAxis` — без изменений (переиспользуются).

### Ключевые решения

- **Универсально (решение юзера):** правка в `resolveOverlapsAlongFlow`, единственный
  вызывающий — `resolveOverlapsInWrapper`, общий для контейнер-scope (1025) и ⌘⇧F.
  Оба пути чинятся без плaмбинга и флагов. AC#2 трактуется как «не регрессировать
  push **внутри** полосы»; cross-lane drag убирается на обоих путях (он нежелателен
  везде).
- **Frontend-only:** push живёт только во фронте; backend `apps/backend/src/domain/layout.ts`
  resolve-overlaps не вызывает → бэкенд не трогаем.
- **Pinned — без изменений:** внутри полосы pinned-узел стоит и двигает курсор
  (поведение `resolveOverlaps1D`).
- **Геометрические полосы (не компонентные):** определяются по поперечному
  перекрытию текущей геометрии, без графа рёбер. В frame-pack модели (DRW-218
  `packComponents` раскладывает компоненты в разные поперечные полосы с зазором)
  геометрические полосы ≈ компоненты, но не требуют рёбер в точке push.

### Граничные случаи

- **Деградация корректна:** если выросший контейнер реально дотянулся до полосы
  соседа (поперечное перекрытие появилось) — они в одной полосе и push сработает.
  Геометрия берётся на момент push (после роста бокса).
- **Узлы одного flow-ряда, разной высоты, выровненные** → перекрываются поперечно →
  одна полоса (push сохранён).
- **«Один ряд» но с реальным поперечным зазором** → разные полосы → push не нужен
  (узлы не наезжают; не регресс).
- **Не-cardinal направление** → ось из геометрии (`flowAxis` fallback), поперечная —
  другая; полосы считаются так же.
- **Транзитивный мост:** цепочка узлов с непрерывным поперечным перекрытием
  объединяется в одну полосу — это визуально контактная полоса, push по ней
  допустим. В наблюдаемом баге между полосами чистый зазор → моста нет.

## Out of scope (follow-up задача)

**VPSC 2D node-overlap removal** (`solve1D` в `@shemma/domain`; Dwyer/Marriott
«Fast node overlap removal»): полноценное минимальное 2D-смещение с separation-
ограничениями, подключение в оба пайплайна (frontend `elk-layout.ts` + backend
`layout.ts`), в перспективе замена `resolve-overlaps.ts` + `findEmptySlot`.
Решает более широкий класс (полосы реально сталкиваются и нужна 2D-разводка),
которого в наблюдаемом баге нет. Заводится отдельной backlog-задачей.

## Тестирование

### Юнит (`apps/frontend/src/canvas/resolve-overlaps.test.ts`)

`groupLanes`:
- одна полоса (все узлы выровнены поперечно);
- две чистые полосы (зазор > LANE_EPS) → два массива;
- касание/перекрытие ровно на LANE_EPS → разные полосы (строгое `> LANE_EPS`);
- транзитивный мост (A∩B, B∩C, A∌C) → одна полоса;
- не-cardinal (ось из геометрии) → корректная поперечная ось;
- детерминизм порядка полос и узлов.

`resolveOverlapsAlongFlow` (lane-aware):
- две полосы, наезд только в одной → moves только для её узлов, вторая не в выводе;
- перекрытие **внутри** полосы → push сохранён (регресс легитимного поведения DRW-232);
- pinned внутри полосы — опора, не двигается, двигает курсор;
- reverse-направления (RL/BT) — зеркаление по полосам корректно.

### Регресс-фикстура (mirrors live repro)

Тест: фрейм LR, контейнер растёт вширь, X-цепочка в нижней полосе (поперечно не
пересекается) → её координаты по оси потока не меняются. (= AC#3.)

### Live-верификация (координатор, chrome-devtools)

Room `drw242-repro` (оставлен как ручная фикстура): повторить сценарий
репродукции → X-цепочка **не** двигается, зазоры остаются ровными. Делает main
agent сам (не доверять скриншот-отчётам субагентов).
