**Версия:** 1.2 · **Дата:** 2026-06-12 · **Статус:** реализована; AC#1-7 пройдены live (Task 8) + фикс по live-приёмке, ждёт финальной приёмки юзера

## 1. Проблема

Текущая 2-уровневая схема (контейнер = чёрный ящик: внутренняя раскладка отдельно,
root-прогон отдельно) не видит **внешних** связей детей контейнера. Следствия — оба
эталона приёмки Фазы 1 (скрины в `docs/superpowers/specs/assets/2026-06-12-drw235-*`):

1. **Порядок строк не согласован между контейнерами** — узел стоит не напротив
   своего партнёра (эталон 1: before/ideal).
2. **Сквозная цепочка зигзагом** — A1→B1→D1→E1 скачет по строкам, хотя «спокойно
   может развернуться в линию по верху» (эталон 2: chain-zigzag/chain-topline).

## 2. Решение (зафиксировано юзером 2026-06-12)

Архитектура **(c)-global-y** — модель, считанная с идеал-скрина юзера и подтверждённая
probe-сессией и live-пробой прототипа:

- **x и состав колонок** — без изменений: текущий root-прогон ELK (контейнеры-боксы,
  партиция компонент DRW-218, направления Фазы 1).
- **Порядок строк** в каждой колонке — топология внутренних рёбер (Kahn) + median-score
  внешних соседей; решения принимаются по **выровненным** позициям (чередование
  «свип порядка → выравнивание»).
- **Координата поперёк потока** (y на LR/RL-доске, x на TB/BT) — **глобальный
  1D-решатель** по всем узлам компоненты сразу: минимизация |Δc| по cross-рёбрам
  при separation-ограничениях (VPSC).
- **Контейнеры обтягивают** результат: бокс = строки + padding, контейнер
  растягивается (разрыв между строками допустим — как C1/C4 на идеал-скрине).

### Почему не альтернативы (probe-данные, топология drw-218-stability)

| Метрика | (a) barycenter-постпасс | (b) иерархич. ELK | **(c)-global-y** |
|---|---|---|---|
| Цепочка A1→B1→D1→E1 (разброс cy) | 110px ❌ | 35px ≈ | **0.0px** |
| A3↔E2 | 72px ❌ | 0px | **0.0px** |
| Per-container direction | да | **нет** (per-node `elk.direction` игнорируется при `INCLUDE_CHILDREN` — probe-b2) | да |
| Идемпотентность | n/a | 0px (semiInteractive) | 0px (live) |

(a) — наивный barycenter ломает внутренние рёбра (порядок A1,A3,A2), честная версия =
переписывание layered-логики ELK вручную, зигзаг остаётся. (b) — контейнеры с
внутренними рёбрами ложатся вдоль направления доски (C1 → широкая двухслойка вместо
колонки), что противоречит эталону и направлениям Фазы 1.

### Live-проба прототипа

- Эталонная комната: точное воспроизведение идеала (3 линии, растяжение C4),
  идемпотентность 0px.
- Сложная схема (8 контейнеров / 36 узлов / 40 стрелок): лейны формируются,
  идемпотентно, **но** прототип внёс 5 box-перекрытий среди top-level элементов
  (baseline 0) — separation-ограничения были только внутри колонок.
  **→ центральное требование §3.1.**

## 3. Дизайн

### 3.1. VPSC-solver в `@shemma/domain` (новый модуль `layout-solver.ts`)

Одномерный решатель «минимальное суммарное смещение при separation-ограничениях»
(Variable Placement with Separation Constraints, Dwyer/Marriott) — **общий для
DRW-235 (выравнивание) и DRW-242 (2D-пуш)**. WebCola — референс алгоритма,
НЕ зависимость.

```typescript
export interface SolverVar {
  id: string;
  pos: number;          // стартовая координата (центр)
  size: number;         // протяжённость по решаемой оси
  weight?: number;      // вес желания (по умолчанию 1)
  fixed?: boolean;      // pinned: переменная не двигается
}
export interface SeparationConstraint {
  left: string;         // id переменной «выше/левее»
  right: string;
  gap: number;          // pos(right) − pos(left) ≥ gap; pos — ЦЕНТРЫ, т.е.
                        // gap = (size(left) + size(right)) / 2 + зазор краёв
}
export interface AlignmentGoal {
  a: string;
  b: string;            // желание: pos(a) === pos(b) (cross-ребро)
  weight?: number;
}
export function solve1D(
  vars: ReadonlyArray<SolverVar>,
  constraints: ReadonlyArray<SeparationConstraint>,
  goals: ReadonlyArray<AlignmentGoal>,
): Record<string, number>;
```

Требования: детерминизм (стабильные сортировки, без рандома); блочное слияние
выровненных групп (лечит «взаимную погоню» пар, которую прототип обходил
чередованием направления обхода); `fixed`-переменные (пины); сходимость
гарантирована (VPSC — конечный алгоритм, не итеративная эвристика прототипа).

### 3.2. Constraint-граф для выравнивания (frontend-пасс)

Переменные: дети участвующих колонок (поштучно), loose top-level узлы,
непартиципирующие top-level элементы (контейнеры вдоль потока, sizePinned-контейнеры)
— **как единый бокс-вар** (их дети едут вместе с боксом).

Ограничения:
1. **Внутри колонки:** порядок строк (после ordering) + `gap = rowGap`
   (`csp.nodeNode × CONTAINER_SPACING_FRACTION`).
2. **Между top-level элементами:** для каждой пары с пересекающимися интервалами
   по оси потока — separation по cross-оси (порядок = текущий) с зазором `sp.nodeNode`.
   Это закрывает дыру live-пробы (перекрытия 5 → 0). Так как высота обтянутого
   контейнера зависит от решения, цикл: solve → re-wrap боксов → rebuild
   top-level-ограничений → solve (2 раунда достаточно; детерминированно).
3. **Цели:** cross-рёбра (центр↔центр), вес 1.

Пины: `meta.pinned`-узел → `fixed`; контейнер с pinned-детьми → ordering для него
пропускается (как у flip-пасса), pinned-дети — fixed-вары внутри колонки.
`didrawSizePinned`-контейнер не растягивается → участвует как бокс-вар целиком.
`forceUnpin` (⌘⌥⇧L) снимает все вето на один пасс — как в Фазе 1.

### 3.3. Ordering (валидирован прототипом, переезжает как есть)

`orderColumn`: Kahn по внутренним рёбрам колонки; среди доступных — узел с меньшим
score (median c внешних соседей; без внешних — текущая позиция); цикл → исходный
порядок. Свипы по колонкам в порядке оси потока; **первый свип направленный**
(score только от уже переупорядоченных колонок и loose — отсекает зеркальные
решения «главная цепочка не по верху»); чередование «свип → выравнивание»
до неподвижной точки (≤4 циклов).

Ordering **заменяет flip-пасс** для участвующих колонок (строго сильнее зеркала);
flip остаётся для непартиципирующих контейнеров.

### 3.4. Оси и направления

Доска LR/RL → выравнивается y, колонки = TB/BT-контейнеры. Доска TB/BT → симметрично
x, «колонки» = LR/RL-контейнеры. Реализация через ось-абстракцию (main/cross),
без дублирования кода. Контейнер с направлением ВДОЛЬ потока доски не участвует
строками (его дети — горизонтальная цепочка), едет как бокс-вар.

### 3.5. Обтяжка и re-pack компонент

После решения: бокс колонки = [min(строка) − padTop, max(строка+h) + padBottom];
размер пишется в props контейнера (как сейчас). Компоненты re-pack'аются по
cross-оси заново (рост боксов меняет габариты компоненты): главный держит исходный
верх, последующие — последовательно с зазором `sp.comp`. Партиция DRW-218
сохраняется: рёбра и ограничения не пересекают границы компонент.

### 3.6. Порты — явный выход для Фазы 3 (DRW-199)

Пасс возвращает `portHints: Map<edgeId, { source: Pt; target: Pt }>` — точки
входа/выхода cross-рёбер на границах контейнеров (для выровненных рёбер —
горизонталь/вертикаль через центры узлов). Сейчас потребитель —
`distributeArrowPorts` (прямые рёбра получают точные анкоры), в Фазе 3 — роутер.
Не персистится.

### 3.7. Интеграция

- Хук в `runElkLayout` на месте прототипа (после flip-пасса, до anchor-offset),
  **флаг убирается** — пасс становится штатным для `algorithm === "layered"`
  (Tree/Stress/Force — без выравнивания, поведение Фазы 1).
- dryRun (aspect-search) метрики считаются ДО пасса — без изменений
  (выбор направления не зависит от выравнивания).
- `global-align.ts` рефакторится: ordering остаётся во frontend (знает о колонках),
  итеративный решатель заменяется на `solve1D` из `@shemma/domain`.
- **Backend parity** (`apps/backend/src/domain/layout.ts`, путь scope='subgraph'):
  отдельная задача в конце фазы — тот же solver из domain, чтобы `shemma_layout`
  (MCP) давал тот же результат, что ⌘⇧L. Допустимо вынести в follow-up при срыве
  объёма фазы (зафиксировать задачей, не молча).

## 4. Acceptance criteria

Live (комнаты-копии уже в dev-storage: `drw-235-probe`, `drw-235-probe2`):

1. **Эталон 1 (порядок):** force-пасс на drw-235-probe даёт порядок по внешним
   связям: C2=[B1,B2], C3=[D1,D2,D3], C4=[E1,E2].
2. **Эталон 2 (линии):** цепочка A1→B1→D1→E1, ряд A2→B2→D2 и пара A3↔E2 — каждая
   на одной горизонтали (|Δcy| < 1px); C4 растянут под нижний ряд.
3. **Без новых перекрытий:** на drw-235-probe2 пасс не вносит box-перекрытий
   среди siblings (baseline 0 → 0). Закрывается VPSC-ограничениями §3.2-п.2.
4. **Идемпотентность:** повторный пасс на обеих комнатах — 0 сдвигов.
5. **Гарантии Фазы 1 сохранены:** партиция (правка одной компоненты не двигает
   другую), sticky-направления, пины (не-force пасс не двигает pinned), локальность.
6. **Per-container направления сохранены** (TB-колонки остаются колонками).
7. **Locked-фреймы** (a-elk-tree, dl-test) не затронуты.
8. Solver `solve1D` — в `@shemma/domain`, покрыт юнитами, интерфейс пригоден для
   DRW-242 (подтверждается тестом-примером «overlap removal»).
9. Существующие тесты workspace зелёные; флаг `__SHEMMA_GLOBAL_Y` удалён.

## 5. Out of scope

- Роутинг рёбер / obstacle avoidance — Фаза 3 (DRW-199, спайк DRW-244).
- Вложенные контейнеры (рекурсия >2 уровней) — модель Фазы 1 сохраняется.
- Иерархический ELK, fcose, structure-detection — «за горизонтом» (Фаза 4+).
- 2D-пуш DRW-242 — отдельная задача, но solver делается совместимым (AC#8).
- UI-настройки выравнивания.

## 7. Риски

1. **VPSC-имплементация** — самый алгоритмичный кусок. Митигация: компактный
   алгоритм (satisfy + project/split по Dwyer/Marriott), эталонные тесты против
   результатов прототипа (числа уже сняты), WebCola как референс.
2. **Цикл solve→re-wrap→solve не сойдётся за 2 раунда** на патологии. Митигация:
   жёсткий лимит раундов + AC#3 как стоп-критерий; в худшем случае остаются
   старые позиции (пасс best-effort, как layout в domain-мутациях).
3. **Расхождение frontend/backend** до задачи parity. Митигация: явная задача
   в плане; известное временное состояние.
4. **Производительность** на больших досках (сотни узлов): solver O(n log n)-класс,
   пасс на компоненту; ELK-прогоны остаются доминирующей стоимостью.
