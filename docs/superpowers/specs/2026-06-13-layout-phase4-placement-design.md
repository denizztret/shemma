# Layout Фаза 4: пере-размещение блоков — дизайн (DRW-246 + DRW-247)

**Версия:** 1.1 (2026-06-13)
**Статус:** DRW-246 принят на приёмке (drw-235-probe — «отличный результат»). **DRW-247 ИЗЪЯТ из фазы на приёмке** (см. §10) и переоткрыт на радиальный редизайн. Фаза 4 = только DRW-246.
**Ветка:** `feature/layout-phase4-placement`

## 1. Контекст и цели

Фидбэк приёмки Фазы 3 (2026-06-13):

1. **DRW-246 (HIGH):** arc-дуги — паллиатив. Когда libavoid-обход невыразим штатной
   elbow-стрелкой (U / детур / Z вне диапазона), естественнее **подвинуть блок**, чтобы
   маршрут стал выразимым, чем рисовать дугу. Дуга остаётся fallback'ом.
2. **DRW-247 (MEDIUM):** ELK layered ставит каждый узел в свой слой — листья-сиблинги
   растягиваются в длинную линию. Слабосвязанные блоки можно укладывать **компактно
   рядами** (сеткой) рядом с хабом.

Обе задачи ослабляют жёсткую слоистость по метрикам, не ломая гарантии Ф1–Ф3:
идемпотентность, детерминизм, no-surprise (только явная компоновка ⌘⇧L/⌘⌥⇧L),
пины неприкосновенны.

## 2. Решения (приняты в рамках делегирования)

| Вопрос | Решение | Обоснование |
|---|---|---|
| Приоритет сдвига vs дуги | Сдвиг пробуем ПЕРЕД принятием дуги; дуга — fallback | Прямое пожелание юзера |
| Где живёт сдвиг | Внутри routing-пасса (Ф3), вторым прогоном | Невыразимость известна только после libavoid |
| Оценка кандидатов сдвига | Dry-run libavoid на гипотетических боксах, БЕЗ записи в editor | Дёшево (~12мс), детерминированно |
| Кого двигать | Только leaf, unpinned, ≤2 инцидентных рёбер; конец с меньшей степенью | Минимальное вмешательство |
| Компактная укладка — механизм | «Супер-узел» ДО ELK (по аналогии со strays), разворот ПОСЛЕ | ELK сам обеспечивает зазоры; ноль коллизий |
| Пучок (bundle) | ≥3 листа с ровно одним ребром, все к одному хабу, unpinned | 2 листа в линию — норм; меньше риска |
| ELK-опции вместо своего пасса | Отклонено | compound layout не используется; supernode проще и детерминирован |

## 3. DRW-246 — сдвиг блоков вместо arc-дуг

### 3.1 Поток

`runEdgeRoutingPass` (edge-routing.ts), после первого `decideEdges`:

1. Собрать **shift-цели**: решения с `plan.kind ∈ {U, detour}` (т.е. `action`
   получился `arc` или `inexpressible`).
2. Для каждой цели — `planBlockShift` (чистая логика + dry-run роутинг):
   выбрать подвижный конец, сгенерировать позиции-кандидаты, оценить каждую
   повторным libavoid-роутингом на копии боксов, выбрать лучшую прошедшую гейт.
3. Если приняты сдвиги: применить их (`editor.run`: x/y подвижных шейпов в
   координатах родителя + re-fit обёрток), затем **повторить весь routing-пасс**
   (рекурсия глубиной 1, флаг `internal.depth`), который сделает обычный writeback.
4. Если сдвигов нет — поведение Ф3 без изменений (arc/inexpressible как раньше).

### 3.2 Подвижный конец и кандидаты

Подвижный конец (eligibility, оба конца проверяются, предпочтение по порядку):
`kind === "leaf"` && `!meta.pinned` && инцидентных рёбер ≤ 2. Из двух пригодных —
меньшая степень, затем меньшая площадь, затем конец `to` (детерминизм).
Нет пригодного → цель пропускается (остаётся дуга/inexpressible).

Кандидатные позиции (страница, потом перевод в координаты родителя):

- **Same-parent** (оба конца в одном родителе): 4 позиции вплотную к партнёру
  (по центру каждой стороны, зазор `SHIFT_GAP = 24`) + выравнивание центров
  по поперечной оси потока (flow-координата сохраняется).
- **Cross-parent**: только внутри СВОЕГО родителя (clamp в его внутренние границы
  с padding): выравнивание центров с партнёром по поперечной оси + «к фасаду» —
  сдвиг к внутренней границе родителя на стороне, обращённой к партнёру.

Все кандидаты — список фиксированного порядка (детерминизм tie-break по индексу).

### 3.3 Гейт принятия сдвига

Кандидат принят, если в dry-run прогоне:

1. Целевое ребро стало выразимым: `plan.kind ∈ {straight, L, Z}`.
2. `routeScore` целевого ребра строго меньше лучшего текущего (стар. маршрут или дуга).
3. Нет новых наездов боксов: `countBoxOverlaps(after) ≤ countBoxOverlaps(before)`.
4. Суммарный `routeScore` по всем рёбрам затронутого класса не ухудшился.

Из прошедших — минимальная сумма score, затем длина целевого, затем индекс кандидата.
Сдвиги применяются последовательно (после каждого принятого — обновлённые боксы);
повторный полный прогон делает финальную истину.

### 3.4 Интерфейсы

Новый модуль `apps/frontend/src/canvas/edge-routing-shift.ts` (чистый, без tldraw):

```ts
export interface ShiftTarget {
  readonly edge: RouteEdge;
  readonly planKind: "U" | "detour";
  readonly currentScore: number;   // score лучшего текущего варианта (вкл. дугу)
}
export interface ShiftCandidate {
  readonly moveId: string;
  readonly x: number; readonly y: number; // новая page-позиция бокса
  readonly label: string;                  // "adj-top" | "cross-align" | "facade" | ...
}
export function pickMovableEnd(
  edge: RouteEdge, boxes: ReadonlyMap<string, RouteBox>,
  degree: ReadonlyMap<string, number>, pinned: ReadonlySet<string>,
): string | null;
export function genShiftCandidates(
  move: RouteBox, partner: RouteBox, parent: RouteBox | null,
  sameParent: boolean, gap?: number,
): ShiftCandidate[];
export function evaluateShift(  // chooses best passing candidate
  target: ShiftTarget, candidates: ReadonlyArray<ShiftCandidate>,
  boxes: ReadonlyArray<RouteBox>, edges: ReadonlyArray<RouteEdge>,
  routeFn: (boxes: ReadonlyArray<RouteBox>, edges: ReadonlyArray<RouteEdge>)
    => ReadonlyMap<string, Polyline>,   // инжектируемый dry-run libavoid
): { candidate: ShiftCandidate; newScore: number } | null;
```

Оркестрация в `edge-routing.ts`: `routeFn` строится поверх `classifyEdges` +
`routeClasses` (Avoid уже загружен); запись сдвига — page→parent-координаты через
`getShapeParentTransform`; re-fit обёрток — существующими `reflowAfterFit` /
inline-обтяжкой фрейма (как в call-sites).

### 3.5 Отчёт

`EdgeRoutingReport` расширяется: `shifted: Array<{edgeId, movedId, dx, dy}>`;
записи `inexpressible` получают `from`/`to` (диагностика). `window.__SHEMMA_LAST_ROUTING`
показывает сдвиги. CHANGELOG.

## 4. DRW-247 — компактная укладка листовых пучков

### 4.1 Определение пучка

В scope раскладки (дети контейнера ИЛИ loose geo фрейма): группа узлов, у каждого —
ровно одно инцидентное ребро, все рёбра ведут к одному и тому же узлу-хабу того же
scope, все узлы — geo-листья без пинов (`meta.pinned`/`didrawSizePinned` исключают),
размер группы ≥ 3. Направление рёбер не важно (hub→leaf и leaf→hub равнозначны).

### 4.2 Механизм: супер-узел

По аналогии со `splitStrays` (component-partition.ts):

1. **До ELK**: пучок заменяется одним узлом `__bundle__<hubId>_<i>` с размером
   упакованной сетки (`packBundleGrid`), одним ребром hub→bundle.
2. **После ELK** (контейнер: сразу после `elk().layout`; фрейм: ПОСЛЕ `runGlobalAlignPass`,
   до dryRun-bail/`updateShapes` — чтобы Ф2 двигала пучок как единый бокс и не
   растаскивала листья обратно): супер-узел разворачивается — листья получают
   позиции `bundle.xy + gridOffset`.
3. Flip-пасс и Ф2 видят супер-узел как обычный бокс — совместимо без правок.

### 4.3 Сетка

`packBundleGrid(sizes, flowAxis, gapX, gapY)`: колонки вдоль поперечной оси, ряды
вдоль потока. Число колонок k ∈ [1..n] перебором, выбирается минимальный
`max(W,H)` bbox'а (компактность), tie-break меньший k. Порядок листьев — стабильный
порядок входа (детерминизм). Ячейки выравниваются по верхнему/левому краю ряда/колонки;
gap'ы — те же константы spacing, что в scope (передаются параметрами).

### 4.4 Интерфейсы

Новый модуль `apps/frontend/src/canvas/leaf-bundles.ts` (чистый):

```ts
export interface BundleNode { readonly id: string; readonly w: number; readonly h: number; }
export interface LeafBundle {
  readonly id: string;             // "__bundle__<hub>_<i>"
  readonly hubId: string;
  readonly leaves: ReadonlyArray<BundleNode>;  // стабильный порядок
  readonly w: number; readonly h: number;      // bbox сетки
  readonly offsets: ReadonlyArray<{ id: string; dx: number; dy: number }>;
}
export function detectLeafBundles(
  nodes: ReadonlyArray<BundleNode>,
  edges: ReadonlyArray<{ from: string; to: string }>,
  excluded: ReadonlySet<string>,    // pinned и пр.
  flowAxis: "h" | "v", gapX: number, gapY: number,
  minSize?: number,                 // default 3
): LeafBundle[];
export function packBundleGrid(
  sizes: ReadonlyArray<BundleNode>, flowAxis: "h" | "v",
  gapX: number, gapY: number,
): { w: number; h: number; offsets: Array<{ id: string; dx: number; dy: number }> };
export function expandBundles(
  bundles: ReadonlyArray<LeafBundle>,
  pos: ReadonlyMap<string, { x: number; y: number }>, // позиции супер-узлов после ELK/Ф2
): Array<{ id: string; x: number; y: number }>;
```

Интеграция в `elk-layout.ts`:
- `layoutContainerInternal`: detect → подмена детей/рёбер → ELK → expand в результат.
- `runElkLayout` (frame-level, loose geo): detect → подмена в построении компонентных
  графов → ... → expand после `runGlobalAlignPass`, перед `updateShapes`/dryRun-метриками.
- Routing (Ф3) идёт после — видит уже развёрнутые листья; рёбра пучка тривиальны (L/straight).

## 5. Не входит (YAGNI)

- Сдвиг контейнеров/хабов и сдвиги, требующие смены родителя.
- Пере-размещение по более чем одному блоку на ребро; глобальная оптимизация размещения.
- Пучки с >1 ребром на лист (попарные мостики и пр.); пучки из контейнеров.
- Backend parity (DRW-245 — отдельно, следом); 2D-пуш (DRW-242).
- Выключение arc-дуг по умолчанию (кандидат на следующую фазу после статистики).

## 7. Риски

- **Ф2 vs пучок (фрейм-scope):** разворот ПОСЛЕ align — листья не участвуют в
  alignLoose; супер-узел двигается как один бокс. Риск снят конструктивно.
- **Сдвиг ломает чужие рёбра:** гейт п.4 (суммарный score класса) + повторный полный
  прогон как финальная истина.
- **Осцилляция между прогонами:** ELK детерминирован, кандидаты и tie-break — тоже;
  установившееся состояние воспроизводится. Live-проверка идемпотентности обязательна.
- **U-кейс может не решиться сдвигом** (узкий коридор): остаётся дуга — поведение Ф3,
  не регресс.

## 9. Отклонения от спеки (по факту исполнения, 2026-06-13)

Исполнено subagent-driven (T1–T5) + live-фиксы координатором. Тесты frontend 878 pass / 0 fail, typecheck чист, lint-дельта 0.

- **9.1 Семантика пина для пучков и сдвига сужена до позиционного.** В §3.2/§4.1 исключение
  было «pinned (`meta.pinned`/`didrawSizePinned`)». Live выяснилось: `didrawSizePinned`
  ставит авто-обтяжка текста КАЖДОМУ узлу (origin "fit") — он охраняет только размер.
  Если им исключать, пучки/сдвиг не работали бы НИ на одной обычной доске. Исправлено:
  исключает только **позиционный** пин `meta.pinned`. (коммит `15bbeb9`)
- **9.2 Сдвиг побеждает дугу при равном score.** Принятая arc-дуга обычно имеет score 0
  (foreign=0), а строгий гейт `<` не давал сдвигу её превзойти никогда. Добавлено
  `ShiftTarget.currentIsArc`: для дуги гейт ослаблен до `<=` (elbow-через-сдвиг
  предпочтительнее паллиатива); для inexpressible — строгий `<`. (коммит `09d70ef`)
- **9.3 Пучки иммунны к сдвигу.** Осознанно упакованную сетку сдвиг растаскивал
  (выдёргивал листья к хабу, ломал идемпотентность). `EdgeRoutingOpts.bundleLeafIds`:
  рёбра с концом-листом пучка не становятся целями сдвига (контейнер- и фрейм-уровень,
  включая вложенные контейнеры). (коммит `09d70ef`)
- **9.4 Force-семантика доходит до сдвига.** ⌘⌥⇧L переразмещает и pinned-узлы — добавлен
  `EdgeRoutingOpts.forceUnpin`: под force pinned-set сдвига пуст. (коммит `eeb8777`)
- **9.5 Lane-кандидаты уворота.** Базовых кандидатов (adj/cross-align/facade) не хватало
  для эталона A3→E2 (нужно опустить блок ПОД полосу препятствий коридора). Добавлены
  `lane-after`/`lane-before` — уворот за дальний/ближний край препятствий между концами;
  `genShiftCandidates` получил параметр `obstacles`. Фильтр коридора смотрит И ось коридора,
  И **полосу по оси уворота** (union концов): бокс в том же продольном диапазоне, но далеко
  по перпендикуляру (отдельная цепочка) — не препятствие. (коммиты `7fc6f3d`, `747334d`)
- **9.6 Контейнер растёт за сдвинутым узлом.** Сдвиг мог вынести лист за границы его
  user-size-pinned контейнера → узел висел снаружи. `growWrappersForShapes`/
  `refitWrapperGrowOnly` получили `ignoreSizePin`; refit-колбэк сдвига зовёт с `true` —
  сдвиг (осознанное размещение) растит контейнер даже при user-size-pin; авто-envelope
  по-прежнему пин уважает. (коммит `747334d`)
- **9.7 Live-итоги.** Простая (hub+6 → сетка 3×2, идемпотентно), пин (закреплённый лист
  вне сетки и не сдвинут), средняя (A3→E2: дуга → elbow + E2 в выросшем C4, идемпотентно),
  сложная (codex baseline, 2 фрейма, 12 контейнеров: 0 регрессий, 1 сдвиг + остаточные
  дуги-fallback, combined-идемпотентно). Скрины `docs/references/drw-199-probes/t6-phase4-*`.
- **9.8 Follow-ups (не блокируют):** политика «контейнер растёт за сдвигом даже без force»
  применяется всегда (не только force) — оценить на не-pinned досках; выключение arc по
  умолчанию — после статистики.

## 10. DRW-247 ИЗЪЯТ из Фазы 4 на приёмке (2026-06-13)

Юзер на приёмке drw-247-live: сетка пучков «довольно странный результат». **Подтверждено
координатором вживую:** на звезде хаб→6-листьев сетка (3×2) ставит листья в 2 колонки —
рёбра к ближней колонке elbow, к **дальней — arc** (хаб геометрически не дотягивается без
обхода ближних боксов). Одиночная колонка (штатное ELK-поведение) даёт **0 дуг**. Сетка
срабатывает ТОЛЬКО на звёздах (детект = ≥3 листа с одним ребром к общему хабу) — где она и
вредит; компактность куплена ценой половины дуг. Гейт «по числу листьев» не спасает: дуги
от сетки растут с числом листьев (больше колонок → больше дальних → больше дуг).

**Решение юзера: вариант 1 — изъять сетку, оставить только DRW-246.** Откат (коммит `9af028f`):
удалён `leaf-bundles.ts`(+тест), вся интеграция пучков в `elk-layout.ts` (контейнер- и
фрейм-scope), `bundleLeafIds` из `edge-routing.ts`. Сдвиг (DRW-246) нетронут — live-перепроверен
(A3→E2 по-прежнему elbow+сдвиг dy=188, 0 дуг). hub+6 теперь = одиночная колонка, 6 elbow, 0 дуг
(скрин `t7-drw247-removed-singlecolumn.png`). Frontend 851 тестов, typecheck чист. §9.1/9.3
(пин-семантика пучков, иммунитет пучков к сдвигу) с откатом стали неактуальны.

**DRW-247 переоткрыт (To Do) на РАДИАЛЬНЫЙ редизайн:** компактная раскладка звезды требует
не сетки-в-колонки (в линейном потоке хаб не дотянется), а радиального/балансного фан-аута
(хаб в центре, листья веером — все рёбра чистые). Отдельная задача-движок.
