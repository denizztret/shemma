# Стабильность и детерминизм раскладки (Фаза 1 layout-улучшений)

**Дата:** 2026-06-11 · **Версия:** 1.0 · **Статус:** на ревью
**Задачи:** DRW-218 (зонтичная, auto-direction/мультикомпонентность), DRW-233 (scope расстановки контейнера)
**Milestone:** m-8 Layout · **Ветка:** `feature/layout-stability`

---

## 1. Контекст и проблема

Ядро autolayout — `runElkLayout` (`apps/frontend/src/canvas/elk-layout.ts`): двухуровневая раскладка (step 1 — каждый контейнер внутренне через `layoutContainerInternal` → фикс-бокс; step 2 — фрейм раскладывает боксы + свободные узлы одним плоским ELK-прогоном) + flip-пасс + порт-пасс + writeback с anti-drift. Поверх — `autoLayoutFrame`: aspect-aware поиск направления по dry-run-кандидатам.

Три источника нестабильности (live-репро DRW-218, комната `draw-test-1`):

1. **Несвязные компоненты пакует сам ELK** (`separateConnectedComponents` по умолчанию + `elk.spacing.componentComponent`). Позиции компонент зависят от совокупного bbox → добавление/правка второй схемы деформирует базовую.
2. **Auto-direction скорит по всему графу.** Dry-run-кандидаты `autoLayoutFrame` оцениваются по совокупному aspect/crossings → вторая компонента меняет победителя; смена направления одного контейнера триггерит re-decide всего фрейма.
3. **Глобальный scope триггеров.** Расстановка/смена направления на контейнере пере-раскладывает весь фрейм (DRW-233); flip-пасс рассматривает все контейнеры фрейма → inherit-сосед флипается от чужой правки (DRW-218 AC#7).

## 2. Цели

Гарантии (выбор user'а — все обязательны):

- **Идемпотентность** — повторный прогон без изменений графа даёт байт-в-байт тот же результат.
- **Стабильность (локальность)** — малая правка меняет раскладку локально; нетронутая компонента не сдвигается и не деформируется.
- **Воспроизводимость** — один граф → одна картинка (детерминизм ELK + наш детерминированный код).
- **Без сюрпризов auto-direction** — вторая компонента / смена направления контейнера не переворачивает фрейм.
- **Аккуратность и читаемость** — сквозной критерий: минимум пересечений, наложений; эталоны не деградируют.

## 3. Не-цели (вне scope фазы)

- Cross-boundary crossing minimization — порядок узлов по стороне внешних связей (**Фаза 2, DRW-235**).
- Port-ordering и обход препятствий для стрелок (**Фаза 3, DRW-199**).
- N-уровневая рекурсия вложенности (**DRW-200**) — вложенный контейнер остаётся непрозрачным боксом.
- Кеш layout-результатов компонент (вариант C brainstorm'а) — YAGNI: детерминизм ELK даёт идентичный результат и без кеша.
- ELK-playground панель (DRW-115).

## 4. Утверждённые продуктовые решения

1. Подход — **«компонентный разрез»**: партиция на связные компоненты у нас, ELK получает только связные графы.
2. Размещение компонент — **поперёк направления фрейма**: главная (крупнейшая) первой, остальные по убыванию размера; для TB/BT-фрейма вторичные — колонкой справа от главной, для LR/RL — рядом снизу.
3. Auto-direction — **только по главной компоненте**.
4. Политика триггеров: явное «Упорядочить» по фрейму = глобальная оптимизация; точечные действия (контейнер) = локальный scope.

## 5. Архитектура: компонентный слой

### 5.1. Новый модуль `apps/frontend/src/canvas/component-partition.ts`

Чистые функции без `Editor` (по образцу `flow-chains.ts`), всё покрывается юнитами:

- `partitionComponents(topLevelIds, rootEdges): string[][]` — BFS/union-find по схлопнутым рёбрам root-графа. Компонента = набор top-level элементов (боксы контейнеров + свободные geo).
- `rankComponents(components, info)` — `info: Record<id, {leaves: number; area: number}>` (контейнер → число листьев и площадь бокса; geo → 1 и площадь). Главная = max суммарных листьев; tie-break: суммарная площадь → первый id компоненты (лексикографически; порядок элементов внутри компоненты стабилен и следует input-порядку). Полностью детерминировано.
- `packComponents(ranked, frameDir, gap)` — главная в origin (её ELK-координаты как есть); вторичные стопкой поперёк оси потока с зазором `gap = sp.comp`:
  - TB/BT: `x = main.maxX + gap`, вторичные сверху вниз (`y` накапливается: `+h + gap`);
  - LR/RL: `y = main.maxY + gap`, вторичные слева направо.
  Возвращает смещение `{dx, dy}` на компоненту.

### 5.2. Правило strays (одиночные узлы)

- **Stray** = singleton-компонента из одного свободного **geo** без связей. Одинокий контейнер — полноценная компонента (это схема), не stray.
- Все strays собираются в **один псевдо-компонент**: внутри выстраиваются flow-цепочкой (`buildFlowChainEdges`) **вдоль** направления фрейма; в стопке вторичных встают последними.
- Вырожденный случай «во фрейме нет НИ ОДНОГО ребра на корне» (только несвязанные узлы и/или контейнеры) → ВСЕ top-level элементы образуют единственный псевдо-компонент с flow-цепочкой вдоль направления — текущее поведение «несвязанные дети выстраиваются по направлению» (квик-фаза S6 rebuild) сохранено и для контейнеров. Поперечная стопка включается только когда есть настоящая главная компонента (≥1 ребро).

### 5.2.1. Несвязные компоненты ВНУТРИ контейнера (фикс по приёмке)

- Внутренний граф контейнера тоже бывает несвязным: `C1 = {A1→A2} + изолированный A3`. Без обработки elk-layered ставит изолированный узел в layer 0 **вторым столбцом поперёк** направления (и визуально он «прилипает» к чужой колонке).
- Решение: `layoutContainerInternal` партиционирует детей по внутренним рёбрам (`partitionComponents`), ранжирует (`rankComponents`, главная первой) и связывает соседние компоненты синтетическими **мостами** `__bridge__N` (sink предыдущей → source следующей, `buildComponentBridgeEdges` в `flow-chains.ts`). ELK получает связный граф — все компоненты выстраиваются **вдоль** направления контейнера одной полосой, новых наездов быть не может.
- Порядок компонент внутри полосы — по rank (детерминизм); сортировка по внешним связям — Фаза 2 (DRW-235).

### 5.3. Изменение `runElkLayout` step 2

Вместо одного root-прогона по всему плоскому графу:

1. step 1 (внутренности контейнеров → боксы) — **без изменений**;
2. построение `rootChildren`/`rootEdges` (схлопывание на боксы) — без изменений;
3. **партиция** → ranked-компоненты;
4. **по одному ELK-прогону на компоненту** (те же layoutOptions + явный `elk.separateConnectedComponents: "false"`); корневые flow-цепочки больше не нужны (компонента связна по построению), кроме strays-псевдокомпонента;
5. **пакинг** → смещение каждой компоненты целиком; затем существующая anti-drift нормализация контента к `pad` (top-left фрейма не двигается).

Не меняются: пины (post-override), refit фрейма, writeback, порт-пасс. Flip-пасс и подсчёт crossings — **в пределах своей компоненты** (фильтр пар рёбер по принадлежности компоненте).

Frameless-путь scope-agnostic и получает партицию автоматически (направление — эффективное, как сейчас `DEFAULT_FRAME_DIR`).

**Следствие (DRW-218 AC#1):** нетронутая компонента подаёт в ELK идентичный вход → получает идентичный внутренний layout; добавление второй схемы физически не может деформировать главную.

## 6. Auto-direction: score по главной + липкость + inherited-marker + overlap-term

### 6.1. Score только по главной (AC#2)

Dry-run-кандидаты `autoLayoutFrame` (направление × inherit-режим) оцениваются **только по главной компоненте**: aspect — по её bbox, crossings — по её рёбрам. В dry-run ELK-прогоны вторичных компонент пропускаются (perf). Вторичные раскладываются один раз после выбора победителя, следуя направлению фрейма.

### 6.2. Липкость решения («действующий чемпион»)

Новое meta-поле `frame.meta.didrawDirectionResolved` — направление, фактически применённое последним auto-прогоном (engine-owned, пишется при writeback auto-раскладки; AI/агент его не трогает). В поиске оно заменяет `DEFAULT_FRAME_DIR` как базовый кандидат: претендент обязан **строго** (`<`) побить score чемпиона. При неизменной главной компоненте чемпион скорит одинаково (детерминизм ELK) → направление не дрейфует между прогонами; переключение — только когда правка графа даёт реальный выигрыш. Fast-path сохраняется: чемпион сбалансирован (`ratio ≤ 2.2`) → применяем без поиска.

### 6.3. Inherited-direction marker фрейма (AC#5)

Сейчас `frame.meta.didrawDirection` намертво отключает auto-поиск, а mermaid-импорт пишет его всегда. По образцу контейнеров:

- импорт (backend `schema.ts`) пишет direction + `frame.meta.didrawDirectionInherited: true` → фрейм остаётся auto-eligible, импортное направление участвует как базовый кандидат (чемпион);
- условие в `autoLayoutFrame`: auto выключен только при `didrawDirection && !didrawDirectionInherited`;
- UI: явный клик по cardinal-кнопке направления фрейма чистит маркер (explicit); клик по активной — снимает направление → inherit (та же трёхсостоянийная логика, что у контейнеров).

### 6.4. Overlap-term + perf (AC#6)

Score = `aspectExtremity(main) + 0.15 × crossings(main) + 0.5 × overlaps(plan)`, где `overlaps` — число пересекающихся пар bbox'ов среди top-level узлов плана главной компоненты **плюс все запиненные узлы фрейма** на их замороженных позициях (пины skip'аются в apply, но остаются препятствиями в метрике) — кандидат, наезжающий на пины, проигрывает. Формула и выбор — чистая функция `pickDirectionCandidate(plans, incumbent)`. Perf: кандидаты dry-run'ятся параллельно (`Promise.all`); поиск остаётся только для несбалансированного чемпиона.

## 7. Локализация scope: «раскладывается то, что выделено»

### 7.1. Матрица триггеров

| Действие | Scope |
|---|---|
| «Упорядочить» / ⌘⇧L на фрейме, узле, мульти-выделении или без выделения | Весь фрейм (по компонентам, §5) |
| «Упорядочить» при выделенном **одном контейнере** | Только содержимое контейнера |
| Смена Direction / Движка / Spacing **контейнера** | Только содержимое контейнера |
| Смена Direction / Движка / Spacing **фрейма** | Весь фрейм |
| Frameless-выделение ≥2 page-level узлов | Выделенные узлы (как сейчас) |

Резолвер — чистая функция `resolveLayoutScope(editor, ids)` → `{kind: "frame"|"container"|"loose"|"none", …}`; используется всеми триггерами (⌘⇧L/⌘⌥⇧L, context-menu, панель, сеттеры direction/engine/spacing).

### 7.2. Механика контейнер-scope

`resolveContainerDir` + `layoutContainerInternal` для выбранного контейнера → apply детей + размер бокса, **root-граф фрейма не строится**. Изменение размера бокса разруливают существующие механики DRW-232: `growWrappersForShapes`/`reflowAfterFit` — соседи отодвигаются **сдвигом** (не пере-раскладкой), envelope фрейма растёт. Контракт grow-only сохраняется: при уменьшении бокса соседи назад не подтягиваются (уплотнение — respread DRW-239, вне scope). Порт-пасс и `optimizeElbowMidpoints` — только по стрелкам, касающимся детей контейнера.

### 7.3. Следствия

- **AC#7 (flip-scope) закрывается конструктивно:** смена направления контейнера X не выходит за пределы X — соседи не флипаются, auto-direction фрейма не пересматривается. Глобальный flip-пасс остаётся только в полном «Упорядочить» и ограничен компонентой.
- **forceUnpin на контейнере** игнорит пины только внутри него.
- **Lock фрейма** блокирует и контейнер-scope внутри него (текущее правило).
- Вложенные контейнеры: раскладываются прямые geo-дети выбранного; вложенный контейнер — непрозрачный бокс (DRW-233 AC#3 документировано; рекурсия = DRW-200).

## 8. Данные / meta-поля

| Поле | Владелец | Семантика |
|---|---|---|
| `frame.meta.didrawDirectionResolved` | engine | Направление последнего auto-прогона («чемпион»). Не user-owned; не участвует в pin/style ownership. |
| `frame.meta.didrawDirectionInherited` | engine/import | Направление взято из импорта/auto → переинферируемо. Чистится явным выбором в UI. |

Оба поля игнорируются v1-комнатами без вреда (optional, отсутствие = текущее поведение).

## 9. Тестирование и верификация

1. **Юниты (bun, CI)** — весь детерминизм в чистом коде:
   - `component-partition.test.ts`: партиция, ранжирование (повторный вызов = тот же порядок), пакинг для 4 направлений, strays-правило, вырожденный случай «только одиночки»;
   - `pickDirectionCandidate`: равный score → incumbent; строгое улучшение → переключение; overlap-term с пинами;
   - `resolveLayoutScope`: вся матрица §7.1, вложенность, lock.
2. **Идемпотентность уровня движка** — node-харнесс в `scratch/` (ELK в bun-тестах не запускается — известное ограничение bun/elk-worker): прогон дважды на фикстурном графе → идентичные координаты. Dev-инструмент, не CI; в CI гарантия конструктивная (юниты п.1 + детерминизм ELK как документированное допущение).
3. **Фикстура-репро DRW-218 (AC#3)** — своя тест-комната по мотивам `draw-test-1` (юзерскую не трогать): схема с 4 контейнерами + несвязная цепочка из 5 узлов. Сценарии: (а) добавление цепочки → главная не сдвинулась, цепочка поперёк; (б) смена направления контейнера → изменился только он + envelope-push соседей; (в) повторные ⌘⇧L → ноль дрейфа.
4. **Live-верификация** — итеративно по ходу задач, main-агентом через chrome-devtools MCP (визуальную проверку не делегировать). Эталоны: `a-elk-tree`, `dl-test` — до/после, без деградации (AC#4).
5. **Приёмка** — merge в main + tag только после live-теста user'а. Существующие frontend-тесты (499) зелёные.

## 11. Риски

- **Визуальный сдвиг относительно текущего поведения:** пер-компонентные прогоны + наш пакинг дают другую (лучшую, но другую) картинку для существующих мульти-компонентных фреймов. Митигировано live-проверкой эталонов; одно-компонентные фреймы (подавляющее большинство) не меняются.
- **Допущение детерминизма elkjs:** layered/mrtree детерминированы при фиксированных опциях; проверяется node-харнессом (§9.2). Force использует seed — зафиксировать `org.eclipse.elk.randomSeed` при необходимости.
- **Grow-only envelope при контейнер-scope:** уменьшившийся контейнер оставляет «воздух» — осознанный trade-off (uплотнение = respread), фиксируется в доке поведения.
- **Engine-owned meta:** `didrawDirectionResolved` пишется при каждом auto-прогоне — убедиться, что echo-guard/WS-синхронизация не зацикливаются (writeback уже пишет meta, путь отработан).

## 12. Roadmap следующих фаз (вне scope, для контекста)

- **Фаза 2 — DRW-235:** порядок детей контейнера и контейнеров фрейма согласован со стороной внешних связей (cross-boundary crossing minimization); кандидаты — hierarchical port constraints ELK либо пост-пасс переупорядочивания.
- **Фаза 3 — DRW-199:** port-ordering на узле (порядок якорей соответствует порядку целей) + обход препятствий для остаточных длинных рёбер (multi-bend / RoutedArrowShape из DRW-178).
- **DRW-200:** N-уровневая рекурсия `layoutContainerInternal` + единый каскадный resolver параметров.
