# ADR-0006: Git flow & release policy

## Status

Accepted.

## Context

Репозиторий публичный (`github.com/denizztret/shemma`). Нужна единая,
зафиксированная политика того, как реализуются задачи (ветвление, merge,
коммиты) и как назначаются версии и теги (релизная процедура). Правила уже
действовали де-факто (см. `CLAUDE.local.md` и серию feedback-решений), но были
рассеяны — этот ADR консолидирует их как source of truth.

Цели:

- На публичный `main` попадают только merge-коммиты, release-коммиты и теги —
  никаких одиночных feature/fix/docs коммитов вне ветки.
- Теги не плодятся на каждый merge: тег = настоящий релиз.
- «Релиз» — это полный pipeline (build + publish), а не просто `git push tag`.

## Decision

### Branching (GitFlow)

- **`main`** — production-ready. Прямые коммиты запрещены **без исключений**,
  даже для однострочного фикса. Любое изменение проходит через ветку.
- **`feature/<short-name>`** — новые фазы / крупные feature'ы. От `main`,
  merge обратно в `main`.
- **`fix/<short-name>`** или **`hotfix/<short-name>`** — баг-фиксы. От `main`.
- **`docs/<short-name>`** — правки docs/README/CLAUDE вне feature scope.

### Merge

- Стиль слияния — всегда **`--no-ff`**.
- **Никогда** не делать `rebase` feature-ветки на `main` перед merge.
- **Squash-паттерн:** на feature-ветке `git reset --soft` → squash в логичные
  коммиты (обычно один) → `git merge --no-ff` в `main`. Топология ветки
  сохраняется в графе, ветка остаётся чистой.
- Удалять ветку после merge.

### Commits

- Короткое imperative-описание изменений.
- **Без trailers** `Co-Authored-By:` / `Signed-off-by:` / `Generated by` и
  подобных. Сообщение содержит только описание самих изменений.

### Acceptance gate

- Merge feature→`main` **+ tag** — **только после** live user testing и явного
  acceptance.
- Перед PR/merge: `bun run test` зелёные + `bun run lint` чистый.

### Versioning (SemVer)

- Формат `MAJOR.MINOR.PATCH` ([semver.org](https://semver.org)).
- Pre-1.0 (`0.x.y`): любой **MINOR** может ломать совместимость.
- Между релизами версия берётся из `git describe --tags --dirty`.

### Tags

- Чистые числа **без префикса**: `0.30.0`, **не** `v0.30.0`.
- Тег ставится на `main` **после** release-коммита.
- **НЕ плодить теги на каждый merge** — паттерн tag-per-merge отменён.

### Release triggers

| Триггер | Релиз? | Bump |
|---|---|---|
| Завершена фаза | **да** | MINOR |
| ≥3 fix'ов **+ explicit signal «релиз»** | **да** | PATCH |
| Critical hotfix | **да** (сразу) | PATCH |
| Merge одной ветки / один Backlog task / прошёл интервал | **нет** | — |

**Batch-кластеры:** для multi-task bug-кластеров копим фиксы на `main` без
per-задача release-коммитов и bump'ов — один релиз в конце по явному сигналу.

### Release pipeline

«Релиз» — это весь конвейер, а не только `git push tag`:

1. Bump `package.json` (×9 — все пакеты workspace).
2. Release-коммит.
3. `./scripts/publish-release.sh` → build (`bun build --compile`) + manifest +
   `gh release create`.
4. Тег на `main`.
5. `git merge --no-ff` ветки в `main` (если релиз закрывает feature-ветку).

### Push в origin

Разрешён по GitFlow-workflow выше. Push **тегов** — только при настоящем
релизе, не на каждый merge.

## Rationale

- **`--no-ff` + squash** сохраняет topology ветки в графе и одновременно держит
  историю `main` чистой (один логичный коммит на задачу + merge-commit).
- **Запрет rebase feature на `main`** — feature-ветки публичные; rebase
  переписывает историю и ломает уже расшаренные ссылки.
- **Теги только на релиз** — `git describe --tags --dirty` даёт осмысленную
  dev/debug-версию между релизами, а теги остаются маркерами публичных
  артефактов (бинарь + GH Release), а не шумом на каждый merge.
- **Acceptance gate** — автотестов недостаточно для canvas/layout-задач;
  визуальная регрессия ловится только live-проверкой пользователем.
- **Full pipeline за «релизом»** — пользователи ставят shemma как
  single-binary через manifest; голый git-tag без опубликованного бинаря
  оставит `shemma update` без артефакта.

## Consequences

- Любая задача = ветка + `--no-ff` merge; работа напрямую на `main` исключена.
- Версия в dev-сборках не «красивая» (`0.30.0-5-gabc123-dirty`) — это норма,
  не баг.
- Release-коммит трогает 9 `package.json` — bump автоматизирован в
  `publish-release.sh`, ручная правка версий не нужна.
- Bug-кластеры накапливаются без промежуточных тегов до явного сигнала —
  между ними `main` может быть впереди последнего тега на несколько фиксов.
