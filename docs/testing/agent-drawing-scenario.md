# Тест-сценарий: итеративное агентское рисование (Shop Platform)

Воспроизводимая последовательность заданий агенту (через MCP: Claude Code / OpenCode /
MagnitCopilot / …) для проверки инкрементального AI-редактирования v2 schema-фрейма.
Источник: живая приёмка DRW-205 (2026-06-07) — лог реальной сессии пользователя,
на котором всплыли схлопывание фрейма, displacement-«куча» (DRW-208), дрейф
overlay↔store (DRW-209) и пустые subgraph-блоки schema-group (DRW-210).

## Предусловия

1. Свежая комната (например `agent-scenario-1`), live-вкладка открыта (WS-subscriber).
2. Seed-схема — создать через `shemma_create_schema`:

```
graph LR
  client[Web Client] --> api[API Gateway]
  api --> auth[Auth Service]
  api --> catalog[Catalog Service]
  catalog --> catalogdb[(Catalog DB)]
```

3. **Ручные правки пользователя** (важно — без них пины не появляются):
   подвигать 3–5 узлов, переименовать один двойным кликом, нарисовать одну
   произвольную фигуру руками внутри фрейма.

## Последовательность заданий агенту

После **каждого** шага — чекпоинты (ниже). Шаги давать агенту дословно.

| # | Задание агенту | Что добавится |
|---|---|---|
| 1 | «добавь ещё пару объектов/сервисов — чего не хватает?» → выбрать «поиск и аналитику/логирование» | Search Service, Analytics Service, Logging DB + связи |
| 2 | «добавь Notification Service» | Notification Service (+Queue) ← Orders/API |
| 3 | «добавь ещё дев-логирование» | Dev Logger → Logging DB |
| 4 | «давай добавим CDN сервера» | CDN Edge, CDN Origin (role network), Web Client → Edge → Origin |
| 5 | «не вижу» *(если узлы не видны — фиксируем как баг, агент НЕ должен чинить это полным layout)* | — |
| 6 | «распиши на схеме CDN подробнее» | L1/L2 Cache, Origin Shield, CDN Storage + цепочка |
| 7 | «объедини сервисы в подгруппы» | 4 контейнера: CDN / API Layer / Data Layer / Observability |
| 8 | «покрась сервисы с заливкой Solid» | restyle существующих узлов (color+fill) |
| 9 | «переименуй мою фигуру в DB Backup и включи в схему» | adopt не-схемного шейпа (DRW-212) |

## Чекпоинты после каждого шага

- **Без перевыравнивания:** ни один существующий узел не сдвинулся (особенно
  ручные позиции из предусловий); агент НЕ вызывает `shemma_layout` сам.
- **Без схлопывания:** фрейм не уменьшился; все узлы внутри рамки (effective
  bounds c growY), отрицательных координат нет.
- **Без нахлёстов:** новые узлы не пересекают существующие (по effective h+growY).
- **Размещение осмысленно:** новый узел рядом со связанными (anchor-bias).
- **Стрелки elbow** с лейблами; связи к узлам внутри контейнеров материализуются.

## Финальные проверки (после шага 9)

1. **Группы (шаг 7):** на доске реальные контейнеры, члены внутри, subgraph-блоки
   в raw НЕ пустые (DRW-210).
2. **Restyle (шаг 8):** цвет/заливка изменились на доске сразу, без re-create.
3. **Reload-консистентность:** F5 → доска выглядит ТАК ЖЕ, как в живой вкладке
   (нет дрейфа store↔didrawOverlays, DRW-209).
4. **Явный layout по просьбе:** сказать агенту «сделай аккуратный layout» →
   пины не двигаются, остальное читабельно, БЕЗ «кучи»-колонны (DRW-208),
   ничего за рамкой.
5. **Файл комнаты:** после удаления любого узла нет dangling-биндингов и
   упоминаний в raw; orphan-overlay допустим (keep-dead), opLog ≤ 50 записей.

## Численные проверки (bun-однострочники)

Нахлёсты/выход за рамку/колонны — см. сниппеты в Final Summary DRW-205
(дополнения #1–2): чтение `/api/state`, попарные пересечения effective-bounds,
сигнатура колонны (≥4 узлов на одном x).
