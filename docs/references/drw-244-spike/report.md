## AC#1 — потолок штатной elbow-стрелки: **частично**

Проверено по исходникам tldraw 5.0.0 (`tldraw/src/lib/shapes/arrow/elbow/`):

- Маршрут elbow-стрелки **вычисляется, а не хранится**: `ElbowArrowRoute.points` — derived,
  никакого prop'а/API для произвольной ломаной нет.
- Каталог маршрутов фиксирован (`elbowArrowRoutes.tsx`: L/Z/U-обходы **только двух связанных
  фигур**, до ~5–6 сегментов в U-вариантах). Чужие препятствия (третьи боксы, контейнеры
  между концами) роутер **не видит вовсе** — вход `getElbowArrowInfo` = стрелка + её два биндинга.
- Управляемые степени свободы снаружи: сторона выхода/входа (binding `snap`/`normalizedAnchor`/
  `isPrecise`) + **один скаляр** `props.elbowMidPoint` (положение средней линии). Форму маршрута
  из каталога выбирает сам роутер по взаимному положению концов.

Итого: N-сегментный маршрут libavoid переносится в штатную стрелку **только если** совпадает
с тем, что elbow-роутер сам построил бы при заданных сторонах и midpoint — простые L/Z(/узкие U)
между двумя фигурами. Произвольный детур вокруг третьего препятствия **невыразим**.

Эмпирика на реальной CI-схеме (20 рёбер): сегментов 1×2, 2×7, 3×10, 7×1 —
**19/20 маршрутов ≤3 сегментов** (кандидаты на точный/близкий перенос «стороны + midpoint»),
1/20 — честный 7-сегментный обход (невыразим штатно; сегодня такой случай и есть дефект
«стрелка сквозь контейнер»).

## AC#2 — кастомный arrow-shape: **недели, не дни**

- Объём референс-машинерии tldraw: `ArrowShapeUtil.tsx` 1274 + elbow-роутер ~1.9k +
  `ArrowBindingUtil` 325 + label/targets/heads ~1.3k ≈ **6.5k строк** — это то, чьи контракты
  придётся воспроизводить (рендер + handles + hit-test + биндинги + экспорт).
- Историческая эмпирика: отброшенная попытка `b93f990` (2026-05-26, codex) = ~1.5k строк за
  **display-only** routed-arrow без реактивности — сделана за дни, признана тупиком ровно
  из-за отсутствия binding-реактивности и UX.
- Production-уровень (drag → стрелка тянется: свой `BindingUtil` + re-route по
  `onAfterChangeToShape`; endpoint re-bind UX; waypoint-handles; label вдоль маршрута;
  миграция существующих комнат `arrow`→custom и обратная совместимость v1/v2; mermaid-импорт
  и backend `compile.ts`; сопровождение upstream-изменений tldraw) — оценка **2–4+ недели**.
  Уроки DRW-164/165: даже простые кастомные shape тянут скрытые контракты (getGeometry,
  canResizeChildren).

## AC#3 — WASM в нашем окружении: **подтверждено (bun и Vite)**

`libavoid-js@0.5.0-beta.5` (WASM-порт Adaptagrams).

**bun (headless):** работает из коробки — exports-условие `node` → `dist/index-node.mjs`,
wasm находится сам. Загрузка **16 мс**; 20 рёбер / 22 препятствия — **12 мс**;
инкрементальный re-route после сдвига одного бокса — **4.3 мс**, пересчитано только 7/20
задетых маршрутов; **детерминизм**: два прогона дают идентичные полилинии. Nudging развёл
параллельные рёбра на заданные 16px.

**Vite/браузер (наш dev-фронтенд):** web-entry `dist/index.js` прибандлился штатно;
загрузка WASM **13–23 мс**, роутинг 3 рёбер — 9 мс; маршрут честно обходит препятствие
(3 сегмента).

**Грабли (задокументированы):**
1. exports-карта пакета описывает только `"."` → `import ... from "libavoid-js/dist/libavoid.wasm?url"`
   падает (`Missing "./dist/libavoid.wasm" specifier`). В dev спасает `/@fs/<abs-path>`;
   для прод-сборки нужен `resolve.alias` на wasm или копирование в static assets.
2. embind-enum'ы — статические свойства классов (`Avoid.RouterFlag.OrthogonalRouting`),
   в конструкторы передаётся `.value`; d.ts пакета это не отражает.
3. Аксессор полилинии — `polyline.at(i)` (не `get_ps`); `ConnDirAll` в JS-биндинге
   отсутствует — передавать числом (15).
4. Память emscripten-объектов ручная (`.delete()`); для продакшена — lifecycle-менеджмент
   (router per layout-вызов проще всего).
5. Роутер глобальный: per-edge исключение препятствий невозможно. Вложенность
   («свой контейнер — не препятствие для своих рёбер») решается на уровне модели:
   роутить на уровне контейнеров (portHints Фазы 2 — готовые точки на границах) и/или
   исключать предков из набора препятствий конкретного прогона.

## AC#4 — Вердикт-рекомендация для DRW-199 (Фаза 3)

**Рекомендация: гибрид — «libavoid-as-layout-hint» + штатные elbow-стрелки.**
Runtime custom shape — не делать сейчас.

Адресно по трём доводам решения 2026-05-26:

| Довод «против libavoid» (05-2026) | Статус по spike |
|---|---|
| Теряем нативную binding-реактивность | **Остаётся валиден против runtime-варианта** (AC#2: реактивность пришлось бы строить самим). Layout-hint её **не трогает**: рисуем штатными стрелками. |
| Тащим WASM в runtime | Для layout-hint WASM грузится лениво и только в layout-пасс (16–23 мс load, роутинг единицы мс; bun-вариант для backend-parity работает из коробки). Это не «WASM на каждой доске»; без WASM — деградация до текущего поведения. |
| Нет визуальной выгоды | **Выгода появилась и измерена**: 10/20 реальных рёбер — 3+ сегментов, nudging разводит параллельные рёбра, 1 честный детур. В 05-2026 не было фундамента Ф1/Ф2 (партиция, ordering, portHints), на котором hint-маршруты ложатся на штатные стрелки. |

Схема layout-hint для Фазы 3 (вход в brainstorm, не дизайн):

1. После глобального выравнивания (Ф2) прогон libavoid по итоговым боксам;
   пины — из portHints (точки на границах контейнеров уже есть).
2. Перенос маршрута в штатную стрелку: стороны входа/выхода → binding
   (`snap`/`normalizedAnchor`/`isPrecise`), средняя линия → `elbowMidPoint`.
   По пробе переносимо ~19/20 маршрутов.
3. Невыразимые маршруты (детуры) → метрика «невыразимости»: сигнал к локальному
   пере-размещению узлов (решает причину, а не симптом) либо осознанное elbow-приближение.
4. Fallback всей фазы: расширение собственного elbow-пасса без libavoid
   (ordering Ф2 уже снял большую часть боли).

Пересмотреть runtime custom shape имеет смысл только если после Фазы 3 детур-класс
маршрутов останется частым на реальных досках.

**Решение по принятию рекомендации — за пользователем** (зафиксировано в задаче DRW-244).
